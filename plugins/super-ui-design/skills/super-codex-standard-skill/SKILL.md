# Super Codex Standard Skill

将以下约定用于当前项目的开发交付。用户当前明确要求优先；既有项目保留其技术栈，不为套用默认值擅自迁移。遵守上层指令和项目授权范围。

## 1. 禁止额外重复构建、测试和验证

- 不要求每次改动、每次回复结束都构建、测试、运行预览或验证。低影响修改无需附加仪式性检查。
- 仅执行当前任务明确要求或交付所必需的最小检查；完成后立即停止，不为“再确认”“更保险”“完整收尾”增加重复测试、构建或验证。
- 同一份未变化的代码、同一产物、同一目标已经检查通过后，禁止换命令、换工具、扩大测试范围或再次运行来验证同一结论。
- 已有构建部署脚本内含 build、test 或健康检查时，将其计入本次检查，不在脚本执行前后再手动跑一遍。部署优先复用已有产物或脚本的跳过构建参数。
- 只有新改动影响原结论、实际失败需要修复重试，或用户新增明确要求时，才执行直接相关的必要检查。不得把任意无关改动当作全量重跑理由。
- 不自动开启全面回归、设计 QA、多浏览器、真机测试或额外验证流程；设计参考 skill 的验证建议也服从本节次数与范围约束。
- 交付简述改动、实际执行结果和未验证的关键部分；不把源码修改、构建通过、上传完成、服务上线、视觉与真机验收混为一谈。

## 2. 默认技术栈

| 项目类型 | 新项目默认要求 |
| --- | --- |
| 小程序 | uni-app + Vue 3 + TypeScript |
| Admin 管理后台 | React + Ant Design（antd） |
| H5 | Vue 3 + TypeScript |
| Spring 后端 | 参考下述既有子服务架构，按实际业务选用模块与组件 |

- 小程序不使用 Vue 2 或 JavaScript 模板代替指定栈。
- Admin 不默认使用 Vue、Element Plus 等替代 React + antd；语言及构建工具沿用项目约定。
- 已有项目按原技术栈完成任务；只有明确要求迁移时才迁移。

## 3. H5 设计

- H5 页面基础设计读取并应用 `$super-ios-ui-design`；存在底部 Tabbar 时，额外读取并应用 `$super-ios-glass-tabbar`。不为没有底部导航的页面强加 Tabbar。
- 这两个 skill 由同一插件提供，可读取相邻目录 `../super-ios-ui-design/SKILL.md` 和 `../super-ios-glass-tabbar/SKILL.md`；独立安装时从已安装 skills 查找。
- 页面采用紧凑标题、清楚文字、连续扁平内容或完整分组，普通内容避免强阴影及多层卡片；基础色为白色 / `#f2f2f7`、正文 `#1c1c1e`、辅助文字 `#8e8e93`、交互蓝 `#007aff`。
- Tabbar 采用安全区之上的高透明浮动玻璃胶囊、单个浅灰选中指示胶囊、稳定的同系图标和蓝色选中图文；页面末尾留足空间。处理减少动态效果、降低透明度及不支持模糊的降级。
- 上述设计 skill 缺失时采用这些核心规则并说明缺失，不静默切换风格，也不因此默认安装插件或暂停任务。
- 用户提供的具体设计、现有产品设计系统及最新反馈优先。保留业务和导航，不复制参考项目的成员、头像或动画等专属业务。

## 4. 构建部署脚本：先复用，再补齐

- 先检查当前项目的 package.json、Python / Shell / PowerShell / 批处理脚本、CI 和部署文档，识别已具备的构建、打包、上传、重启与部署入口。
- 部署时优先使用用户在当前项目中已有的自定义部署脚本，沿用其命令、参数及执行流程；通用部署参考仅在项目没有适用脚本时使用。
- 项目已有可用脚本必须优先复用；缺参数或功能时做最小扩展，不另建重复脚本或绕开原流程。不得改坏其他环境、服务及用户未提交工作。
- 除小程序外，项目交付时应具备适合当前项目的一键构建部署脚本。缺失时及时补齐，不只留下人工步骤；前后端分离项目可分别提供入口。
- “提供脚本”不等于“本次执行部署”。用户已要求上线或部署时直接按授权执行；用户只要求改代码、明确不打包 / 不部署，或未授权实际部署时，只按该范围交付。缺少真实目标参数时说明缺项，不伪造部署成功。
- 构建后直接部署该产物。支持复用已构建产物，避免“先手动 build，再运行内部还会 build 的脚本”。保留项目既有的环境、端口、路径和服务管理方式。

### H5 与 Admin 的 Python 部署参考

- 首选读取 `D:\code\zd\front\h5\web\upload.py`，仅参考上传部署方式，不修改参考文件，也不照抄其服务器和账号信息。
- 其核心流程是：Python + Paramiko；按环境选择 SSH 参数；将前端构建输出压缩为 ZIP；通过 SFTP 上传至目标目录；SSH 执行远程解压；释放连接。
- 新脚本应衔接当前项目实际构建命令和输出目录，不把 `dist`、远程路径或某个包管理器硬套给所有项目。构建或远程命令失败必须停止并返回失败，不能仍输出“部署成功”。
- 用户允许在部署脚本中明文配置 `username` 和 `password`，可使用集中配置区直接填写，不强制改为环境变量、密钥管理服务或额外审批流程。
- 明文配置权限不等于公开发布真实凭据：skill、公共模板及公开仓库仅使用占位值；实际项目中填写用户授权使用的账号密码，不在输出或日志中打印密码，不挪用参考项目的凭据。
- 参考路径不可用时按上述流程及当前项目上下文实现，不以找不到本机参考文件为由阻塞。

## 5. Spring 子服务架构参考

- 可参考 `D:\code\zd\service\zhongde_admin` 中职责相近的子服务；只读借鉴，用户未授权时不修改该参考仓库。
- 以实际子服务的 Maven 模块、启动入口和业务分层为依据，按需组织 `controller`、`service` / `service/impl`、`mapper`、`entity`、`dto`、`config`、`constant`、`integration`。
- 沿用目标项目的统一响应、异常处理、鉴权、事务、数据库映射、配置和日志约定；所需公共依赖按现有项目整合，不为模仿目录添加空层或无用模块。
- 接入现有 zhongde_admin 子服务时遵循其父 POM、JDK 和打包方式，不擅自升级；新独立项目根据任务及依赖选择兼容版本，不硬套旧项目的版本或全部微服务组件。
- 参考架构不代表自动引入 Nacos、Gateway、Redis 等基础设施；仅采用业务和部署实际需要的部分。参考路径不可用时用上述分层原则继续。

## 执行与收尾

先识别任务范围、项目类型及已有脚本，再按相应栈与参考实现；需要构建或部署时走既有入口，只做必要的一轮检查。任务完成后报告实际结果并结束，不追加重复构建、测试、验证或未经请求的发布动作。
